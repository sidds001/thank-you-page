SECTION 02

End-to-End Happy Path Flow

This is the golden path — user completes checkout, sees an upsell, accepts, pays, and the item is added to their existing order.

Happy Path — 12 Steps
01
User completes checkout & original payment succeeds
Original order created on Shopify via GoKwik. Payment captured via Easebuzz/PayU. Order status: PAID. GoKwik stores gokwik_order_id, shopify_order_id, original_payment_id.
02
User redirected to GoKwik Thank You Page
TY page loads at *.addons.gokwik.co/thank-you. Page receives: gokwik_order_id, shopify_order_id, merchant_id, order total, items purchased.
03
TY page calls GoKwik Upsell API
GET /api/v1/upsell/recommendations?order_id={gokwik_order_id}&merchant_id={merchant_id}
Backend fetches applicable upsell rules from the rule engine config. Filters by: product/collection purchased, carousel item count. Returns list of upsell products with images, prices, variants, and discount (if configured).
04
TY page renders upsell carousel below order summary
User sees: order confirmation ✓ at top → order summary → upsell section ("Complete Your Look" / "You May Also Like") with product card(s), price, variant selector, "Add to Order" CTA.
05
User clicks "Add to Order"
Frontend sends: POST /api/v1/upsell/initiate with gokwik_order_id, upsell_product_id, variant_id, quantity, upsell_price. Backend validates inventory, price, and creates an upsell_session record with status INITIATED.
06
GoKwik backend initiates PG call for upsell amount
Calls Easebuzz/PayU with: upsell_amount (only the incremental amount), upsell_txn_id (new unique ID like KWIK_UPSELL_{order_id}_{timestamp}), customer email, phone. Returns PG payment link/SDK init params.
07
User completes payment on TY page itself
PG inline/popup payment flow (UPI, Card, etc.) — user can choose a DIFFERENT method than original order. On success, PG sends callback/webhook to GoKwik with upsell_payment_id, amount, status, method.
08
GoKwik receives PG success → Calls Shopify Order Edit API
Step 8a: POST orderEditBegin(id: shopify_order_id) → returns calculatedOrder ID
Step 8b: POST orderEditAddVariant(variant_id, quantity) → appends item
Step 8c: POST orderEditCommit() → finalizes edit. Order now has original items + upsell item.
09
Push upsell transaction to Shopify
POST /admin/api/orders/{shopify_order_id}/transactions.json with kind: "capture", amount: upsell_amount, gateway: "manual" (or custom name). This creates a second transaction record on the same Shopify order — merchant sees both payments on the order details page.
10
GoKwik stores all records internally
Update upsell_sessions status → COMPLETED. Insert into upsell_transactions. Update upsell_analytics (offer shown → accepted → paid → order edited). Link: gokwik_order_id ↔ original_payment_id ↔ upsell_payment_id ↔ shopify_order_id.
11
TY page updates in real-time
Frontend receives success callback → updates order summary to show original items + upsell item + revised total. Upsell section changes to "Added to your order ✓" confirmation state. CTA disabled to prevent re-submission.
12
Merchant sees unified order in Shopify Admin
On the Shopify order details page: all items (original + upsell) under one order ID, two transaction records (original payment + upsell payment), standard fulfillment workflow — ship everything together.

SECTION 04

System Architecture — Service Interaction Map

Five systems interact in this flow. Here's which owns what:

SystemOwnsKey APIs
GoKwik TY Frontend UI rendering, upsell carousel, PG SDK integration, real-time order summary update Calls GoKwik Backend APIs, renders PG inline flow
GoKwik Backend (Orchestrator) Upsell session management, rule engine query, PG initiation, Shopify sync, analytics writes /upsell/recommendations, /upsell/initiate, /upsell/callback, internal Shopify sync workers
Rule Engine (Existing) Merchant-configured upsell rules — product selection, collection mapping, carousel count, discount config Internal DB queries against upsell_rules table
Payment Gateway (Easebuzz/PayU) Payment processing for upsell amount. New transaction ID. Possibly different payment method than original. PG Init, PG Webhook/Callback, PG Status Check
Shopify Admin API Order of record. Order Edit API for appending items. Transaction API for recording payment. orderEditBegin, orderEditAddVariant, orderEditCommit, POST /transactions.json
Critical design decision — Sync strategy: The Shopify Order Edit + Transaction push (Steps 8–9) should be executed as an async background job with retry logic, NOT synchronously in the PG callback. Reason: Shopify API has rate limits (40 requests/second per app) and can be slow. The user should see success on the TY page as soon as PG payment succeeds. The Shopify sync can happen in the background within seconds. If it fails, retry queue picks it up. The upsell_sessions table tracks the state: PG_SUCCESS → SHOPIFY_EDIT_PENDING → SHOPIFY_EDIT_DONE → SHOPIFY_TXN_PUSHED → COMPLETED.

Three new tables, one modified table. This is additive — no existing table structures break.

SECTION 06

Payment Engine — Multi-Transaction per Order

How it works

The original order has Payment ID KWIKG3NYJNM64219984MP for ₹1,212 via UPI on Easebuzz. The user then accepts an upsell for ₹349. A completely new PG session fires:

FieldOriginal PaymentUpsell Payment
Payment IDKWIKG3NYJNM64219984MPKWIK_UP_G3NYJNM_1712645420
Amount₹1,212₹349
Payment MethodUPICard (could be different!)
ProviderEasebuzzEasebuzz (same PG)
StatusSuccessSuccess
GoKwik Order IDKWIKG3NYJNM64219984MP — SAME
Shopify Order ID#4595912 — SAME

Transaction ID generation for upsell

Format: KWIK_UP_{original_order_short_id}_{unix_timestamp}

This ensures uniqueness (timestamp prevents collisions), traceability (contains original order reference), and is identifiable as an upsell transaction by prefix KWIK_UP_.

Idempotency

Critical: Generate an idempotency_key = SHA256(gokwik_order_id + upsell_variant_id + amount) and send it with the PG init call. Store it in upsell_sessions. Before initiating a new PG call, check if a session with this key already exists and is in PG_PENDING or PG_SUCCESS state — if yes, reject the duplicate request. This prevents double charges if the user clicks "Add to Order" multiple times or the page refreshes.
SECTION 07

Shopify Sync — Order Edit + Transaction Push

Step 1: Order Edit (GraphQL Admin API)

Uses Shopify's orderEdit* mutations. This is a 3-call sequence that MUST be atomic — if any call fails, the session rolls back.

// 8a — Begin edit session mutation { orderEditBegin(id: "gid://shopify/Order/7531867832567") { calculatedOrder { id } userErrors { field, message } } } // 8b — Add upsell variant mutation { orderEditAddVariant( id: "gid://shopify/CalculatedOrder/...", variantId: "gid://shopify/ProductVariant/...", quantity: 1 ) { calculatedOrder { id addedLineItems { edges { node { title quantity } } } } userErrors { field, message } } } // 8c — Commit edit mutation { orderEditCommit( id: "gid://shopify/CalculatedOrder/...", notifyCustomer: false, staffNote: "GoKwik Post-Checkout Upsell" ) { order { id name } userErrors { field, message } } }

Step 2: Transaction Record (REST Admin API)

After order edit commits, push the upsell payment as a transaction on the same order:

POST /admin/api/2024-01/orders/{shopify_order_id}/transactions.json { "transaction": { "kind": "capture", "amount": "349.00", "gateway": "gokwik_upsell", "authorization": "KWIK_UP_G3NYJNM_1712645420", "source_name": "gokwik", "currency": "INR" } }
What the merchant sees on Shopify Admin: One order with all items (original + upsell), timeline showing "GoKwik Post-Checkout Upsell" note, two transactions in the payment section (original + upsell amount). The order is ready for standard fulfillment — no special handling needed by the merchant.

Failure handling

Failure PointImpactResolution
orderEditBegin failsNo edit session createdRetry 3× with exponential backoff. If still fails → auto-refund upsell payment via PG refund API.
orderEditAddVariant failsUsually inventory issueDo NOT commit. Auto-refund. Log reason. Alert merchant.
orderEditCommit failsEdit not persistedRetry 3×. If fails → auto-refund. The calculatedOrder expires after ~60 min anyway.
Transaction push failsOrder has the item but no payment record on ShopifyRetry with backoff. This is non-blocking for fulfillment but important for merchant reconciliation. Mark session SHOPIFY_TXN_FAILED and retry via cron.

SECTION 09

Use Cases

UC-01

Happy path — Single upsell, same payment method

User buys Levi's jeans via UPI → sees a belt upsell on TY page → clicks "Add to Order" → pays ₹999 via UPI → belt added to same order → merchant sees 1 order with 2 items and 2 UPI transactions.

UC-02

Happy path — Upsell with different payment method

Original order paid via Credit Card. Upsell paid via UPI. Both payments linked to same GoKwik order ID and same Shopify order. Merchant sees 2 transactions with different methods.

UC-03

Upsell with discount configured

Merchant configures upsell rule with 20% discount. Product MRP ₹545, upsell price ₹436. PG is called for ₹436. Shopify order edit uses the discounted line item price. upsell_discount field stores ₹109.

UC-04

User declines upsell (ignores it)

User lands on TY page → sees upsell carousel → does nothing or scrolls past → leaves page. upsell_offers_log records outcome as SHOWN (impression only). No payment or order edit triggered. Important for conversion rate analytics.

UC-05

Upsell product has variants (size selection)

Upsell product is a T-shirt with sizes S/M/L/XL. Carousel shows variant selector dropdown. User picks "L" → system checks inventory for that specific variant before initiating PG. If "L" is out of stock, variant is greyed out.

UC-06

Multiple products in upsell carousel

Rule configured with carousel count = 3. Three products shown. User can only select and add ONE product per upsell session (Phase 1). After successful add, upsell section shows confirmation. Future phase: allow multiple adds.

UC-07

Upsell rule applies to "All Products"

Merchant selects "Applicable On: All Products" in rule config (as in the screenshot). Every order on TY page shows the configured upsell products regardless of what was purchased. Simple but effective for hero products.

UC-08

Upsell rule applies to "Specific Collections"

Merchant sets upsell rule for "Men's Jeans" collection → only orders containing items from that collection trigger the upsell. Backend matches product.collection_ids against rule config.

UC-09

User revisits TY page (back button / link)

User comes back to TY page after successful upsell. System checks upsell_sessions for this order — finds status COMPLETED. TY page shows the updated order summary (with upsell item) and upsell section in SUCCESS state. No new offer shown. Prevents duplicate upsells.

UC-10

No upsell rules configured for merchant

Recommendations API returns empty array. TY page renders normally without upsell section. upsell_offers_log records nothing — no impression, no click. Page behaves exactly as current production TY page.

SECTION 10

Edge Cases & Failure Scenarios

EC-01

PG payment succeeds BUT Shopify Order Edit fails

Most critical edge case. Money is deducted but item can't be added to order. Resolution: Trigger auto-refund via PG refund API immediately. Set session status REFUND_INITIATED. Send merchant + GoKwik ops alert. User sees "Something went wrong, your payment will be refunded within 5–7 business days."

EC-02

Inventory depleted between offer shown and payment

User sees product at Step 4, but by Step 8b the variant is OOS on Shopify. orderEditAddVariant will return a userError. Auto-refund the upsell payment. Show user "Sorry, this product just sold out." Log for analytics.

EC-03

User double-clicks "Add to Order"

First click creates upsell_session and generates idempotency_key. Second click hits /upsell/initiate again — backend checks idempotency key, finds existing session in PG_PENDING, rejects with "Payment already in progress." Frontend should also disable the CTA on first click.

EC-04

PG timeout — no callback received within 10 minutes

A cron job scans upsell_sessions where status = PG_PENDING AND created_at < NOW() - 10 min. For each, call the PG Status Check API (Easebuzz/PayU both support this). If successful → proceed with Shopify edit. If failed/not found → mark PG_TIMEOUT and close session.

EC-05

Order already in fulfillment when upsell is attempted

Very fast fulfillment merchant ships within minutes. orderEditBegin will fail if order has any fulfilled line items. Mitigation: Before showing upsell, check order fulfillment status. If any item is already fulfilled, skip upsell display. In practice rare for TY page (seconds after order) but must be handled.

EC-06

User closes browser mid-PG flow

PG popup/redirect is open, user closes tab. PG may still complete in background (esp. UPI). PG webhook will arrive at GoKwik backend regardless. If payment succeeded → background job completes Shopify edit. Session goes COMPLETED. If user returns to TY page, they see the updated order.

EC-07

Shopify API rate limit hit (429 error)

Shopify allows 40 req/sec per app. During peak traffic (flash sale), order edits may get throttled. Use exponential backoff: retry after 1s, 2s, 4s, max 3 retries. If all fail, park in retry queue (SQS/Redis) with 60-second delay. Session stays SHOPIFY_EDIT_PENDING. Money is safe — refund only after all retries exhausted.

EC-08

Original order gets cancelled while upsell is in progress

Rare but possible (fraud check, customer calls support). orderEditBegin will fail on a cancelled order. Trigger auto-refund. Mark session SHOPIFY_EDIT_FAILED with reason "Order cancelled."

EC-09

Upsell product is the same as an item already in the order

User bought Product A, upsell shows Product A (same variant). If user adds → Shopify order will have 2 line items or qty=2 for the same variant. Backend should flag this scenario — either skip showing the product or use orderEditSetQuantity to increment quantity instead of adding a duplicate line item.

EC-10

Merchant's Shopify store has order editing disabled

Some Shopify plans or configurations restrict order editing. orderEditBegin returns permission error. Mitigation: During merchant onboarding for upsell feature, verify order edit permissions. If not available, feature is greyed out in GoKwik dashboard.

EC-11

Price mismatch between GoKwik and Shopify

Product price changed on Shopify between recommendation fetch (Step 3) and order edit (Step 8). User was charged old price via PG. When orderEditAddVariant fires, Shopify uses current price. If delta exists → flag discrepancy in upsell_sessions and alert ops. Small deltas can be absorbed; large deltas should trigger review.

EC-12

Partial refund on original order after upsell was added

Customer requests partial refund on original item. The upsell item is still valid and paid. Shopify handles this via standard refund flow — refund the original line item amount. Upsell transaction is separate and unaffected. Merchant must be aware of this in their refund workflow.

EC-13

Multiple PG webhooks arrive for same upsell payment

PG sometimes sends duplicate webhooks. Use upsell_txn_id + payment_id as dedup key. On receiving webhook, check if session is already past PG_SUCCESS state — if yes, ignore. Idempotent processing is mandatory.

EC-14

Shipping cost changes after upsell item is added

If the merchant has weight-based or item-count-based shipping rules, adding an upsell item could change shipping cost. orderEditAddVariant's response includes recalculated shipping. If shipping increases, we have a problem — the upsell PG charge only covered the product price. Phase 1 mitigation: assume free shipping for upsell items or build the shipping delta into the upsell price. Document for dev team discussion.

EC-15

GoKwik backend goes down after PG success but before Shopify edit

PG payment succeeded, webhook received, but GoKwik service crashes before Shopify edit. On restart, a recovery job queries upsell_sessions WHERE status = 'PG_SUCCESS' AND updated_at < NOW() - 5 min and resumes the Shopify edit flow. This is why the state machine is critical — it enables recovery from any crash point.

Phase Roadmap

PHASE 1 Core Upsell Flow (This Build)

  • GoKwik TY page upsell section — carousel with product cards
